# Engineering Principles — ToolNG

> Нормативні правила проєктування та рев'ю. Цей документ не стверджує, що всі механізми вже реалізовані.

## Контекст репозиторію
Windows host-side diagnostics і read-only evidence. Unknown/incomplete evidence ніколи не позначається як успіх.

Пріоритет: коректність → безпека → зрозумілість → супроводжуваність → продуктивність. Не додавайте залежність, мову чи абстракцію без конкретної потреби. Зберігайте API та поведінку, якщо breaking change не обґрунтований окремо.

## Чотири інженерні принципи

### 1. «Штора» — межі та інкапсуляція
- Один модуль — одна зрозуміла відповідальність; публічна поверхня мінімальна.
- Внутрішній стан прихований; назовні виходять типізовані операції, результати й помилки.
- Межі проходять через явні інтерфейси; циклічні залежності заборонені.
- I/O, платформа, час, мережа й файлові системи ізолюються за адаптерами, коли це виправдано.
- Не створюйте універсальні шари, що лише перенаправляють виклики.
**Критерій:** модуль тестується окремо; залежності й побічні ефекти видимі.

### 2. «Волна» — контрольований потік даних
- Потік явний: input → validation → transformation → result.
- Кожен етап визначає формат даних, власника, допустимі стани й помилки.
- Асинхронність та події застосовуються лише за потреби; порядок, timeout і cancellation визначені.
- Shared state мінімізується; перевага immutable values або вузько контрольованій мутації.
- Логи й telemetry не змінюють результат та не розкривають секрети.
**Критерій:** потік простежується; детерміновані операції відтворюються.

### 3. «Бегунок» — обмежене покрокове виконання
- Довгі операції мають кроки, preconditions, postconditions і стан прогресу.
- Для циклів, буферів, черг, повторів і ресурсів задані capacity, timeout, retry budget або cancellation.
- Для помилки визначено stop, retry, rollback чи degraded result.
- Уникайте прихованої роботи в getters, constructors, destructors і UI rendering.
- Оптимізуйте після профілювання, не замість коректності.
**Критерій:** немає необмежених повторів/накопичення; прогрес і зупинка відтворювані.

### 4. «Сепсис» — санітарія архітектури
- Виявляйте дублювання, dead code, застарілі API, циклічні залежності й непотрібні пакети.
- Видаляйте борг малими змінами з тестами до/після.
- Не маскуйте помилки catch-all, silent fallback або фальшивим успіхом.
- Unknown залишається unknown; відсутність доказу не є доказом справності.
- Partial/planned не називаються production-ready.
**Критерій:** кожне очищення підтверджене тестом, аналізом або реально видаленим мертвим кодом.

## «Ржавый» стиль і Rust
«Ржавый» означає сувору дисципліну в будь-якій мові: явне володіння ресурсами, контроль життєвого циклу, типізовані помилки, перевірка меж, мінімум глобального стану й відсутність undefined behavior.

Rust додавайте лише за наявності технічної потреби. Для Rust-коду: cargo fmt --check, cargo clippy --all-targets --all-features -- -D warnings (якщо сумісно), cargo test. unsafe потребує вузького обґрунтування, safety contract і тестів. Не переписуйте C/C++/Python/Swift лише заради моди.

C/C++: ownership/lifetime явні, перевірка меж і переповнень, compiler warnings та sanitizers. Python: type hints на межах, чисті функції, контроль винятків і залежностей. Swift: чітка concurrency isolation, value semantics, мінімум force unwrap.

## Definition of Done
1. Зміна має конкретну мету й обмежений scope.
2. Форматування та lint виконані штатними інструментами.
3. Тести покривають нормальний, граничний і помилковий сценарії.
4. Релевантні build/test/check запущені; неперевірені платформи названі.
5. Немає секретів, зайвих персональних даних або непотрібної telemetry.
6. Документація відповідає коду; partial/planned позначені чесно.
7. Контракти збережені або зміна версіонована й має міграційний шлях.

## Code review
Відхиляйте складність без користі. Вимагайте обґрунтування нових залежностей, глобального стану, unsafe, прихованого I/O та breaking changes. Перевіряйте timeout, cancellation, partial failure і ресурсні межі там, де вони релевантні. Не зливайте зміни з невідомим або негативним результатом перевірок.
