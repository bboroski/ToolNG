# Мовна ясність і термінологічна послідовність

**Статус:** рекомендаційний стандарт документації  
**Сфера:** ToolNG  
**Мета:** точна, зрозуміла й послідовна мова без зайвих запозичень.

## 1. Принцип

Мова документації має пояснювати систему, а не створювати враження фаховості за допомогою жаргону. Якщо українське слово точно передає зміст і не спотворює усталену технічну семантику, надаємо перевагу українському слову. Це редакційна настанова, а не заборона іншомовної лексики чи вимога перекладати кожен термін.

Для цього репозиторію правило застосовується насамперед до таких матеріалів: назви інструментів, довідку CLI, параметри запуску, повідомлення про помилки та інструкції користувача

## 2. Рекомендовані відповідники

| Надмірне або нечітке запозичення | Бажаний відповідник | Уточнення |
|---|---|---|
| meeting / sync | зустріч / нарада / узгодження | Вибирати за реальною дією |
| feedback | зворотний зв'язок / відгук | «Відгук» — оцінка; «зворотний зв'язок» — канал відповіді |
| deadline | кінцевий строк / гранична дата | Не плутати дату й тривалість |
| case | випадок / приклад / практичний розбір | Залежить від контексту |
| skill | навичка / уміння | Розрізняти здатність і практичне володіння |
| feature | функція / можливість | «Функція» — конкретна дія; «можливість» — доступна властивість |
| workflow | порядок роботи / робочий процес | Для послідовності операцій |
| pipeline | ланцюжок обробки / конвеєр | Усталений термін можна пояснити при першій згадці |
| issue | завдання / проблема / запит | Не використовувати один переклад для різних сутностей |
| feedback loop | цикл зворотного зв'язку | Зберігати значення замкненого циклу |
| deployment | розгортання | Не підміняти цим словом складання чи встановлення |
| monitoring | спостереження / моніторинг | «Моніторинг» допустимий як усталений термін |
| configuration | налаштування / конфігурація | Відрізняти дію від структури параметрів |
| performance | швидкодія / продуктивність | Обирати відповідно до вимірюваної властивості |
| reliability | надійність | Не ототожнювати з доступністю |
| security | безпека | Уточнювати модель загроз і межі гарантій |

Це словник-підказка, а не автоматична таблиця замін. Точність важливіша за формальне «очищення» тексту.

## 3. Що не перекладаємо механічно

Без окремого рішення не змінюємо:
- назви проєктів, брендів, репозиторіїв, пакетів і зовнішніх продуктів;
- ідентифікатори коду, назви функцій, змінних, класів, полів, команд, аргументів CLI, шляхів і змінних середовища;
- публічні API, ABI, протоколи, формати файлів, ключі JSON, заголовки мережевих повідомлень та сумісні машинні контракти;
- точні назви стандартів, специфікацій, архітектур, мов програмування й інструментів;
- терміни, для яких переклад створить неоднозначність або суперечитиме галузевому стандарту.

Під час першої згадки можна подати українське пояснення, а далі — усталений термін або скорочення: «інтерфейс програмування застосунків (API)», «двійковий інтерфейс застосунку (ABI)».

## 4. Правила написання

1. Пишемо українською мовою в українських документах; англомовні матеріали зберігаємо англійською, не змішуючи мови в одному реченні без потреби.
2. При першій згадці пояснюємо вузький термін; скорочення розшифровуємо.
3. Обираємо один відповідник для одного поняття в межах документа й пов'язаних сторінок.
4. Назви станів реалізації — «реалізовано», «частково реалізовано», «заплановано» — використовуємо лише відповідно до коду та перевірок.
5. У повідомленнях про помилки називаємо причину, місце й можливу дію, а не обмежуємося жаргонною міткою.
6. Не змінюємо чинні інтерфейси, назви символів або поведінку програми лише заради стилістики.

## 5. Перевірка змін

Перед злиттям документаційної правки перевірити:
- чи зрозумілий текст новому учаснику без внутрішнього жаргону;
- чи не змінився технічний зміст після заміни слова;
- чи однаково названо поняття в README, довідці, прикладах і повідомленнях;
- чи залишилися незмінними код, машинні контракти, посилання та команди;
- чи відповідають заяви про можливості наявній реалізації й тестам.

Для автоматизованої перевірки допускається словник підозрілих запозичень із контекстними винятками. Він має видавати попередження для редакторського перегляду, а не безумовно переписувати файли. Технічні ідентифікатори, цитати, назви стандартів і зовнішні фрагменти виключаються з автоматичної заміни.

## 6. Критерій прийняття

Документація вважається узгодженою, коли терміни послідовні, зміст точний, іншомовні назви збережені там, де вони є частиною контракту, а читач може зрозуміти призначення компонента без знання внутрішнього жаргону.

**Межа цього стандарту:** він задає редакційну політику. Сам по собі він не доводить локалізацію інтерфейсу, не додає перекладів до програми та не змінює поведінку виконуваного коду.
